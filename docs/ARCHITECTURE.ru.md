# Архитектура WindowManager

Документ описывает фактическую архитектуру WindowManager и алгоритмы восстановления, реализованные в текущем коде. Он предназначен для сопровождения: здесь указано, что сохраняется, как выбирается целевой дисплей и как автоматическое восстановление обрабатывает нестабильную конфигурацию и частичные результаты.

Английская версия: [`ARCHITECTURE.md`](ARCHITECTURE.md)

## Назначение и компоненты

WindowManager — macOS-приложение на SwiftUI + AppKit, работающее из Menu Bar. Оно сохраняет раскладки окон и восстанавливает их через Accessibility API. SwiftUI отвечает за главное окно, список раскладок, форму сохранения и экран разрешений; AppKit — за status item, приложения, дисплеи и жизненный цикл; `UserDefaults` хранит раскладки локально; `ApplicationServices` читает и изменяет frame окон сторонних приложений.

```text
WindowManagerApp
├── ContentView / LayoutListView / SaveLayoutSheet
├── PermissionsView
├── StatusBarService
├── ScreenMonitorService
├── WindowService
├── LayoutStorageService
└── PermissionsService
```

При запуске `WindowManagerApp` создаёт и передаёт в SwiftUI `WindowService`, `PermissionsService` и `LayoutStorageService`. После готовности главного представления настраиваются `StatusBarService` и `ScreenMonitorService`. После закрытия главного окна приложение продолжает работать из Menu Bar.

## Сохраняемые модели

`Layout` содержит идентификатор, имя, массив `windows`, дату создания, необязательную дату `lastUsed` и необязательную `screenConfiguration`. `LayoutStorageService` сохраняет массив раскладок как JSON с датами ISO-8601 в `UserDefaults` по ключу `SavedLayouts`. Явный локальный экспорт резервной копии использует ту же кодировку `[Layout]` и атомарно записывает выбранный пользователем файл; он не изменяет `SavedLayouts`, не импортирует и никуда не отправляет данные.

### WindowInfo

`WindowInfo` — сохранённое описание одного окна:

| Поле | Значение |
| --- | --- |
| `id` | UUID, по которому окно связывается между попытками и retry |
| `appName` | Локализованное имя приложения |
| `bundleIdentifier` | Необязательный bundle ID; при наличии предпочтительнее имени |
| `windowTitle` | Заголовок AX при захвате |
| `axRole`, `axSubrole` | Необязательные метаданные Accessibility для сопоставления |
| `frame` | Абсолютный frame в координатах `NSScreen` |
| `relativeFrame` | Необязательный нормализованный frame относительно дисплея |
| `screenID` | Необязательный идентификатор текущего наблюдения дисплея |
| `savedDisplayFrame`, `savedVisibleFrame` | Геометрия дисплея при захвате |
| `preservePresentation` | Не нужно ли зажимать frame для fullscreen/maximized-представления |
| `savedScale` | Необязательный backing scale при захвате |
| `screenIndex` | Индекс дисплея; сохраняется как legacy fallback |
| `timestamp` | Время захвата |

Старый JSON остаётся читаемым: новые поля необязательны. Для старых раскладок используются fallback-ветки resolver, а не отказ в загрузке.

### ScreenConfiguration

Конфигурация экранов хранит отсортированные ID дисплеев, их количество и (для актуальных снимков) отсортированные записи с ID, frame, visible frame и backing scale. Если доступен `NSScreenNumber`, ID имеет вид `screen_<number>`; иначе он строится из геометрии дисплея.

Эти ID — ключи текущего наблюдения, а не постоянная аппаратная идентичность. После hot-plug macOS может назначить номер заново. Поэтому resolver использует ID только при наличии непустого уникального совпадения в текущем снимке. Vendor/model/serial fingerprint не сохраняется.

## Захват раскладки

`WindowService.captureCurrentLayout()`:

1. Требует разрешение Accessibility.
2. Перебирает запущенные обычные приложения, которые не завершены.
3. Читает AX-окна и получает заголовок, role, subrole, позицию и размер.
4. Использует дисплей с `CGMainDisplayID()` как якорь преобразования AX/Quartz → `NSScreen`, а не `NSScreen.main`, зависящий от фокуса клавиатуры.
5. Пропускает окна меньше 50×50 points и окна, не пересекающие объединение текущих дисплеев.
6. Назначает окно дисплею с максимальной площадью пересечения.
7. Сохраняет абсолютный и нормализованный frame, метаданные дисплея и метаданные сопоставления.

Нормализованный frame вычисляется так:

```text
x      = (window.x - display.x) / display.width
y      = (window.y - display.y) / display.height
width  = window.width  / display.width
height = window.height / display.height
```

AX/Quartz использует начало координат сверху и ось Y вниз, а `NSScreen` — начало снизу и ось Y вверх. `WindowCoordinateConverter` выполняет преобразования в обе стороны относительно primary display.

## Восстановление раскладки

`WindowService.restoreLayout(_:, windowIDs:)` восстанавливает всю раскладку либо только окна из переданного набора UUID. Метод возвращает `RestoreResult` с `WindowRestoreResult` для запрошенных целей, когда результат можно определить. Retry использует стабильные ID, а не позиции элементов массива.

Для каждой цели сервис:

1. Вычисляет дисплей и target frame через `ScreenResolver`.
2. Ищет запущенное приложение по сохранённому bundle identifier; цели без него используют fallback по локализованному имени. Сохранённый bundle identifier является обязательным и должен совпасть с текущим.
3. Один раз читает текущие AX-окна приложения и сопоставляет их через `WindowAssigner` по title/role/subrole/frame.
4. Устанавливает frame назначенному AX-элементу.
5. Возвращает статус, полученный из операций AX и read-back, а не просто из успешного запроса установки.

### Выбор дисплея и frame

`ScreenResolver` выбирает дисплей в порядке:

1. уникальный непустой `screenID`;
2. дисплей, содержащий центр сохранённого frame;
3. сохранённый `screenIndex`;
4. первый дисплей в детерминированном порядке.

Абсолютный frame используется без пересчёта только если сохранённые display frame, visible frame и scale полностью совпадают с текущими. Иначе конечный frame строится из конечного `relativeFrame`, если он конечен. Если relative frame отсутствует, сохраняется абсолютный frame как legacy fallback. Если `preservePresentation` не включён, frame зажимается так, чтобы полезная полоса title bar оставалась в текущем visible frame; размер окна без необходимости не уменьшается.

### Запись AX и read-back

`FrameRestoreEngine` записывает позицию, делает короткую паузу, записывает размер, снова делает паузу, повторно записывает позицию и читает позицию и размер. При drift выполняется ограниченная коррекция. Возможные статусы:

- `positionSet` — read-back совпал с целью;
- `appImposedClamp` — приложение приняло запрос, но оставило другой frame;
- `axFailure` — операция записи или чтения AX завершилась ошибкой;
- `restoreSuperseded` — восстановление было вытеснено до завершения read-back;
- `coordinateUnavailable` — не найден конвертер primary display;
- `appNotFound`, `windowSkipped` и другие статусы сопоставления — цель не была назначена.

`RestoreResult.windowsRestored` считает только `positionSet`. Статус `windowMatched` означает состояние сопоставления и не считается восстановленным окном.

## Жизненный цикл Auto-apply

`ScreenMonitorService` наблюдает `NSApplication.didChangeScreenParametersNotification` с debounce 0.5 секунды. Каждое новое событие конфигурации отменяет ожидание стабильности, retry и ожидающее уведомление.

Если Auto-apply включён (ключ `autoApplyEnabled` в `UserDefaults`, значение по умолчанию — `true`):

1. Сервис опрашивает конфигурацию дисплеев каждые 0.25 секунды.
2. Требует три последовательных одинаковых снимка; в снимке учитываются геометрия и scale.
3. Если стабильность не достигнута за 10 секунд, auto-apply пропускается: нестабильная топология не считается безопасной.
4. Ищет раскладки по ID экранов и, если обе конфигурации содержат геометрию, по полному равенству `ScreenConfiguration`.
5. Выбирает наиболее недавно использованную подходящую раскладку; раскладки без `lastUsed` идут после использованных.
6. Записывает в ограниченный 20 событиями in-memory log состояния `started`, `completed`, `noMatch` или `cancelled`.
7. Записывает `lastUsed` как время последней попытки применения; это поле не доказывает успешное восстановление каждого окна. В UI оно называется «Последняя попытка».

Отсутствующие приложения и окна повторяются не более трёх раз с интервалом одна секунда. Набор retry вычисляется по `WindowRestoreResult.id`; перемешанный или разреженный массив результатов не связывает статус не с тем окном. Retry выполняется только для текущего поколения топологии и пока Auto-apply включён. Изменение топологии или выключение переключателя инвалидирует callbacks и предотвращает дальнейшие записи.

Финальное уведомление откладывается до окончания исходной попытки и ограниченных retry либо до отмены retry переключателем Auto-apply. Для одной попытки уведомление отправляется не более одного раза и сообщает число окон с финальным статусом `positionSet`. Фактическая доставка зависит от разрешения уведомлений macOS.

UI хранит последний `RestoreResult` и историю в памяти максимум из 20 результатов. Проверенные `positionSet` показываются отдельно от пропущенных/отсутствующих окон, ошибок AX и ограничений приложения. «Повторить только отсутствующие / ошибочные» — явное ограниченное ручное действие по стабильному `WindowRestoreResult.id`; просмотр диагностики сам по себе retry не запускает. В скопированной диагностике по умолчанию нет имён приложений и окон; они добавляются только после включения переключателя явного согласия.

## Ручные и Menu Bar-сценарии

`LayoutListView` и `StatusBarService` используют один и тот же путь `WindowService.restoreLayout`. Меню status item обновляется при открытии и содержит сохранённые раскладки, сохранение текущей раскладки, переключатель Auto-apply, открытие окна и выход. Сохранение из Menu Bar открывает главное окно и отправляет `ShowSaveLayoutAlert`, который обрабатывает `ContentView`.

## Обратная совместимость и ограничения

- До первого подтверждённого импорта раскладки остаются в `UserDefaults`; затем авторитетен приватный файл в Application Support. Импорт и экспорт только локальные и ручные, без синхронизации; импортированные раскладки исключены из Auto-apply.
- Отсутствующие новые поля `WindowInfo` и `ScreenConfiguration` поддерживаются у старых раскладок. В этом случае используются fallback по центру frame, индексу или абсолютному frame, и точная идентичность дисплея не заявляется.
- Приложение не запускает отсутствующие приложения.
- Динамические заголовки и меняющийся набор окон могут помешать сопоставлению; bundle ID и AX role улучшают его, но не гарантируют результат.
- Приложения могут отклонять AX-изменения, зажимать frame или менять его после read-back. Статус отражает этот результат и не выдаёт его за успех.
- Для захвата и восстановления нужен Accessibility. Screen Recording проверяется эвристически через доступ к списку окон.
- ID дисплеев могут измениться после переподключения; normalized coordinates адаптируют геометрию, но не доказывают, что это тот же физический монитор.
- В автоматизированной проверке не выполнялась живая мутация GUI/дисплеев. У scheme WindowManager нет test action, поэтому `xcodebuild test` для этой цели недоступен.

## Подтверждение проверки

Реализация проверена на утверждённом коммите: Debug-сборка завершилась успешно, focused harness-проверки policy и сопоставления результатов, проверки reopen lifecycle и diff-check прошли, рабочее дерево было чистым. Harness-проверки включают 17 проверок Auto-apply policy, 4 проверки retry-сопоставления по стабильным ID и случаи read-back frame. Это проверки чистой и внедряемой логики, а не замена живого GUI-теста.

Команда сборки:

```bash
xcodebuild \
  -project WindowManager.xcodeproj \
  -scheme WindowManager \
  -configuration Debug \
  -destination 'platform=macOS' \
  build
```
